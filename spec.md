# Underwater Acoustic HIL Simulator — System Specification

---

## 1. Overview

### 1.1 Purpose

A pseudo real-time hardware-in-the-loop simulator for underwater acoustic modems. Each modem transmits and receives through its real analog front-end while the acoustic channel between modems is simulated digitally on a host PC. The propagation delay inherent to underwater acoustics absorbs the system's processing latency, creating a real-time-equivalent test environment without requiring deterministic FPGA hardware.

### 1.2 Key Benefits

| Compared to | Advantage |
|---|---|
| FPGA-based HIL | Far more complex channel models (multipath, Doppler, noise shaping); standard C++ development; rapid iteration |
| Offline simulation | Exercises actual hardware: transducer tolerances, clock offsets, analog front-end nonlinearities, real modem firmware/DSP |
| Tank/field testing | Repeatable scenarios, controlled multipath, no logistics overhead, parametric sweeps |

### 1.3 Operating Principle

1. A modem generates a transmission that drives its transducer (providing realistic electrical loading)
2. The HIL hardware captures this drive signal digitally via an attenuated ADC tap
3. Captured samples stream to the host PC over USB
4. The host applies the simulated channel (Doppler, multipath, path loss, noise) and produces a receive signal
5. The receive signal streams back to the target modem(s) and is injected through an attenuator into the pre-amplifier input
6. The receiving modem processes the signal identically to a real acoustic reception

The simulated acoustic propagation delay (minimum 100 ms corresponding to 150 m at 1500 m/s) provides the time budget for steps 2–5.

## 2. Definitions and Conventions

All stream directions are defined **from the modem's perspective**:

| Term | Definition |
|---|---|
| **TX stream** | The modem's transmitted signal, captured by the HIL ADC through an output attenuator. Data flows modem → host. |
| **RX stream** | The simulated received signal, generated by the host and injected through an input attenuator into the modem's pre-amplifier. Data flows host → modem. |
| **Upstream** | Data flowing from a modem to the host (TX samples, status reports). |
| **Downstream** | Data flowing from the host to a modem (RX samples, commands). |
| **Channel** | A directed signal path from one modem to another (A→B and B→A are separate channels). |
| **Tap** | A single multipath component: complex gain and delay. |
| **Scenario** | A complete test configuration: modem positions, velocities, channel parameters, noise environment. |

## 3. System Architecture

### 3.1 Hardware Configuration Per Modem

```
                          ┌─────────────────────────────────────────┐
                          │              MODEM                      │
                          │                                         │
   Transducer ◄───────┬──┤  Power Amp ◄── Modulator                │
   (load only)        │  │                                         │
                      │  │  TR Switch (open in HIL mode)           │
                      │  │      │                                   │
                      │  │  Pre-Amp ◄── [Input Attenuator] ◄──────── RX stream
                      │  │                                    from  │   (from host)
                      │  │                                   host   │
                      │  │                                         │
   TX stream ◄────────┼──┤  [Output Attenuator] ◄── ADC tap       │
   (to host)          │  │   on transducer drive voltage           │
                      │  │                                         │
                      │  │  USB HS ◄──────────────────────────────── Host PC
                      │  │  (data + control)                       │
                      │  └─────────────────────────────────────────┘
                      │
                      └── Transducer always connected for TX
                          (realistic electrical load)
                          TR switch prevents acoustic coupling to RX path
```

**Key hardware points:**

- The transducer remains connected to the power amplifier during HIL mode to present a realistic electrical load (impedance, back-EMF). The TR switch isolates the receive path so no acoustic energy from the transducer reaches the pre-amplifier.
- The **output attenuator** scales the high-voltage transducer drive signal down to ADC-safe levels for capture.
- The **input attenuator** scales the host-generated RX signal to levels appropriate for the pre-amplifier input. Two selectable attenuation settings are available (approximately 30 dB apart) to accommodate different signal amplitude scenarios.
- The **TR switch settling time** is a minimum of 200 ms after TX ends, allowing residual transducer energy to dissipate before the receive path reconnects.

### 3.2 Network Topology

```
   ┌─────────┐     USB HS      ┌──────────┐     USB HS      ┌─────────┐
   │ Modem A ├──────────────────┤  Host PC ├──────────────────┤ Modem B │
   └─────────┘   (dedicated     │ (Linux)  │   (dedicated     └─────────┘
                  controller)   └──────────┘    controller)
```

- One USB cable per modem to the host PC.
- Each modem should be on a **separate USB host controller** to avoid shared-bus contention and ensure independent, low-latency transfers.
- MVP: 2 modems (2 USB ports on separate controllers).
- Future: up to 6 modems. For more than 4, a USB hub may be required on some ports; bandwidth is not a concern (see §3.3), but latency impact of hubs should be characterized.

### 3.3 Bandwidth

At the nominal sample rate of 500 kSPS:

| Parameter | Value |
|---|---|
| Sample rate | 500,000 samples/s |
| Bytes per sample | 2 |
| Raw data rate per stream | 1.0 MB/s (8 Mbps) |
| USB HS practical bulk throughput | ~35 MB/s |
| Streams per modem | 1 (half-duplex: TX or RX, never both) |
| Headroom per USB link | > 30× |
| 6 modems aggregate | 6 MB/s — well within a single USB controller, but separate controllers are used for latency |

Bandwidth is not a limiting factor for USB HS at any planned modem count or sample rate.

### 3.4 Host PC Specifications

| Parameter | MVP Specification |
|---|---|
| Processor | Intel Core i5 8th generation, desktop (6 cores, 6 threads) |
| OS | Linux with low-latency kernel (PREEMPT) or RT kernel (PREEMPT_RT) |
| Thread affinity | Channel processing and I/O threads pinned to dedicated cores |
| USB | Minimum 2 USB 3.0/2.0 ports on separate host controllers |

## 4. Communication Protocol

### 4.1 USB Device Model

Each modem presents as a **USB vendor-class bulk device** with two interfaces:

| Interface | Direction | Packet Size | Purpose |
|---|---|---|---|
| **Data interface** | Bidirectional (half-duplex) | 512 bytes | Streaming TX/RX sample data |
| **Control interface** | Bidirectional | 64 bytes (fixed) | Commands, status, calibration, metadata |

### 4.2 Data Packet Format

Each data packet is exactly **512 bytes**, aligning with the USB HS bulk maximum packet size:

```
┌──────────────────┬──────────────────────────────────┐
│  Packet ID (2B)  │  255 samples × 2 bytes (510B)    │
└──────────────────┴──────────────────────────────────┘
         Total: 512 bytes
```

| Field | Type | Description |
|---|---|---|
| `packet_id` | `uint16_t` | Monotonically incrementing sequence number. Wraps at 65535 → 0. Used to detect dropped or out-of-order packets. |
| `samples[255]` | `uint16_t[255]` | Sample data. Format depends on direction (see §5.2). |

At 500 kSPS, this yields approximately **1,961 packets/second** per modem stream.

**Direction semantics:**
- When the modem is in **TX mode**: packets flow upstream (modem → host), containing captured TX samples.
- When the modem is in **RX mode**: packets flow downstream (host → modem), containing simulated RX samples.

### 4.3 Control Packet Format

Control packets are **64 bytes, fixed size**, exchanged on the control interface. These carry commands (host → modem) and status (modem → host).

**Status (modem → host) contents include:**

| Field | Description |
|---|---|
| Modem state | Current state: IDLE, TX, RX, SETTLING (see §4.5) |
| Buffer fill level | Current RX/TX buffer occupancy, used by host for pacing |
| Active attenuation | Which input attenuation level is currently selected |
| Error flags | Buffer underrun/overrun indicators |

**Commands (host → modem) include:**

| Command | Description |
|---|---|
| Request calibration | Modem responds with calibration data (see §5.1) |
| Enter HIL mode | Modem configures TR switch, attenuators, and begins streaming |
| Exit HIL mode | Return to normal operation |
| Select attenuation | Switch input attenuator setting (high/low) |

The exact command/status encoding is a firmware design detail. The specification requires that modem state and buffer fill level are reported at a rate sufficient for the host to maintain buffer targets (at minimum once per millisecond, achievable with 64-byte control packets).

### 4.4 Protocol Sequence

```
Host                                    Modem
  │                                       │
  │──── Request Calibration ─────────────►│
  │◄──── Calibration Response ────────────│
  │                                       │
  │──── Enter HIL Mode ─────────────────►│
  │◄──── Acknowledge ────────────────────│
  │                                       │
  │  ┌─── Modem in RX mode ──────────────┤
  │  │    Host streams RX (noise)        │
  │──┤◄───────────────────────────────────│
  │  │    Modem reports status/fill       │
  │  └───────────────────────────────────►│
  │                                       │
  │  ┌─── Modem initiates TX ────────────┤
  │  │    Host detects via status/data    │
  │◄─┤    Modem streams TX samples       │
  │  │    Host stops sending RX          │
  │  └───────────────────────────────────►│
  │                                       │
  │  ┌─── Modem finishes TX ─────────────┤
  │  │    TR switch settling (200ms)      │
  │  │    Modem returns to RX mode       │
  │──┤    Host resumes RX streaming      │
  │  └───────────────────────────────────►│
```

### 4.5 Modem State Machine

```
              Enter HIL
                 │
                 ▼
            ┌─────────┐
            │  IDLE/RX │◄────────────────────┐
            │(receiving│                     │
            │ RX from  │                     │
            │  host)   │                     │
            └────┬─────┘                     │
                 │                           │
          Modem initiates TX            TR switch
          (detected via control         settled
           status + TX data flow)       (200ms)
                 │                           │
                 ▼                           │
            ┌─────────┐              ┌───────┴──┐
            │   TX    │──TX ends───►│ SETTLING │
            │(sending │              │(TR switch│
            │ TX to   │              │ 200ms)   │
            │  host)  │              └──────────┘
            └─────────┘
```

**State transitions from the host's perspective:**

| Transition | Host detection mechanism | Host action |
|---|---|---|
| IDLE/RX → TX | Control packet reports TX state; TX data packets begin arriving | Stop sending RX. Begin receiving and buffering TX samples. |
| TX → SETTLING | Control packet reports SETTLING or TX data packets stop | Stop expecting TX data. Prepare RX stream for when modem returns to RX. |
| SETTLING → IDLE/RX | Control packet reports RX state; 200 ms minimum has elapsed | Begin sending RX stream (signal + noise or noise only). |

**MVP simplification:** The host detects TX start implicitly when TX data packets begin arriving on the data interface, confirmed by the modem state field in control packets. The transition to SETTLING/RX is detected similarly.

### 4.6 Half-Duplex Behavior

The modem is acoustically half-duplex. At the USB level:

- During **RX mode**: only downstream data packets flow (host → modem). The modem does not send data packets upstream (only control packets).
- During **TX mode**: only upstream data packets flow (modem → host). The modem does not accept data packets downstream (only control packets).
- During the **TX→RX transition**, there may be a brief overlap where the last asynchronous USB transfer in one direction completes while the first transfer in the other direction is initiated. The modem discards any residual RX data received during TX or settling; the host discards any residual TX data received after the modem reports transition to settling/RX.

## 5. Calibration and Signal Format

### 5.1 Calibration Data Structure

Requested by the host upon connection. Reported once (or on demand) before entering HIL mode.

```c
struct CalibrationData {
    uint8_t  adc_bits;                  // ADC resolution (e.g., 16)
    uint8_t  dac_bits;                  // DAC resolution (e.g., 12)
    uint8_t  num_input_attenuations;    // Number of selectable RX attenuation levels (2)
    uint16_t noise_floor;               // Modem self-noise floor in ADC counts (RMS or peak)
    uint16_t loopback_cal_attenuation;  // Attenuation setting used during loopback calibration
    float    loopback_gain;             // Measured end-to-end gain: DAC output → attenuator →
                                        //   pre-amp → modem RX processing → modem TX →
                                        //   transducer → attenuator → ADC
    uint32_t adc_sampling_rate;         // TX stream sample rate (Hz), e.g., 500000
    uint32_t dac_sampling_rate;         // RX stream sample rate (Hz), e.g., 500000
    float    input_attenuation[2];      // RX path attenuation (dB) for each selectable setting
                                        //   e.g., [-10.0, -40.0] (30 dB apart)
    float    output_attenuation;        // TX path attenuation (dB), e.g., -60.0
};
```

### 5.2 Sample Formats

| Path | Resolution | Type | Zero-signal value | Full-scale range | Dynamic range |
|---|---|---|---|---|---|
| TX (ADC capture) | 16-bit | `uint16_t` | 32768 (2^15) | 0 – 65535 | ~96 dB |
| RX (DAC injection) | 12-bit | `uint16_t` | 2048 (2^11) | 0 – 4095 | ~72 dB |

**Conversion to/from floating-point processing format:**

```
// TX: ADC sample to normalized float [-1.0, +1.0)
float x = ((float)adc_sample - 32768.0f) / 32768.0f;

// RX: normalized float to DAC sample [0, 4095]
uint16_t dac_sample = (uint16_t)clamp(x * 2048.0f + 2048.0f, 0.0f, 4095.0f);
```

The 12-bit DAC is the dynamic range bottleneck at 72 dB. The channel model processes in `float` (32-bit, ~150 dB dynamic range), with quantization applied only at the final DAC conversion.

### 5.3 Signal Level Calibration

The calibration values establish the relationship between digital sample values and the physical signal levels in the HIL analog path:

1. **`output_attenuation`**: The gain (in dB, negative) from the transducer drive voltage to the ADC input. Allows the host to reconstruct the physical drive voltage from the captured ADC values.
2. **`input_attenuation[k]`**: The gain (in dB, negative) from the DAC output to the pre-amplifier input. Allows the host to determine the DAC output level needed to produce a desired voltage at the pre-amp.
3. **`loopback_gain`**: Measured end-to-end gain through the complete HIL signal path at a known attenuation setting (`loopback_cal_attenuation`). Provides a single-point calibration reference for validating the full path gain.
4. **`noise_floor`**: The modem's self-noise level in ADC counts. The host must inject ambient noise at a level **above** this floor (after accounting for input attenuation and pre-amp gain) so the modem perceives realistic ambient noise levels.

The host uses these values along with the scenario-defined path loss, TVR/RVR, and desired SNR to scale signals appropriately throughout the processing chain.

### 5.4 Sample Rate

| Parameter | MVP Value | Notes |
|---|---|---|
| Nominal sample rate | 500 kSPS | ~50× the signal bandwidth (10 kHz); headroom allows future reduction |
| ADC rate = DAC rate | Yes (MVP) | Different modems may differ in the future; handled via calibration |
| Minimum viable rate | ~100–200 kSPS | 10–20× bandwidth; reduces USB load and processing proportionally |

The host uses the modem-reported `adc_sampling_rate` and `dac_sampling_rate` for all rate-dependent processing. The architecture is rate-agnostic.

## 6. Channel Model

### 6.1 Processing Pipeline

For each directed channel (source modem A → receiver modem B), the host applies the following processing chain. Steps marked **(post-MVP)** are omitted in the MVP.

```
Modem A TX samples (uint16_t, 16-bit ADC)
    │
    ▼
[1] Convert to float, remove DC offset
    │
    ▼
[2] Scale by output_attenuation to recover drive voltage (relative)
    │
    ▼
[3] (post-MVP) Voltage-to-current filter (transducer impedance model)
    │
    ▼
[4] (post-MVP) Apply TVR (transmit voltage response → acoustic domain)
    │
    ▼
[5] Doppler resampling (Farrow interpolator)
    │  Accounts for: clock offsets + radial velocity + acceleration
    │
    ▼
[6] Multipath filter (complex tapped delay line)
    │  Up to 10 taps, delays up to 200 ms
    │
    ▼
[7] Frequency-dependent path loss (absorption + spreading)
    │
    ▼
[8] ──► Accumulate into Modem B's RX mix buffer ◄──  (other channels)
         │
         ▼
    [9]  Add ambient noise (shaped: Wenz + tonal)
         │
         ▼
    [10] (post-MVP) Apply RVR (receive voltage response → electrical domain)
         │
         ▼
    [11] Scale for input_attenuation
         │
         ▼
    [12] Clip to DAC range, convert to uint16_t (12-bit)
         │
         ▼
    Send to Modem B as RX stream
```

**MVP pipeline (steps 3, 4, 10 removed):**

```
TX samples → float → Doppler resample → multipath → path loss → sum → noise → scale → DAC → RX out
```

### 6.2 Doppler and Resampling

#### 6.2.1 Doppler Sources

Two independent effects produce frequency/timing offsets that are indistinguishable from physical Doppler:

| Source | Typical magnitude | Notes |
|---|---|---|
| **Clock offset** | ±10–100 ppm (±0.001–0.01%) | Crystal tolerance between modems. Same for all taps. |
| **Platform velocity** | v/c where v = 0.5–5 m/s, c = 1500 m/s → ±0.03–0.33% | Radial component of relative velocity. |

These combine multiplicatively into a single resampling ratio.

#### 6.2.2 Resampling Model

The key insight is that a modem sampling its own output at its own clock rate sees the signal at its nominal frequency. A receiving modem with a different clock or in relative motion will see the signal at a shifted frequency. The host simulates this by **resampling** the TX stream before injecting it as RX.

**Instantaneous resampling ratio:**

```
          (1 + δ_rx) × (c + v_rx(t))
r(t) = ─────────────────────────────────
          (1 + δ_tx) × (c + v_tx(t))
```

Where:
- `δ_tx`, `δ_rx` = fractional clock offsets (ppm / 1e6) of the transmitting and receiving modems
- `v_tx(t)`, `v_rx(t)` = radial velocities of the transmitting and receiving platforms (positive = moving toward each other)
- `c` = sound speed (1500 m/s nominal)

#### 6.2.3 Acceleration

MVP supports constant acceleration from message start:

```
v_tx(t) = v_tx_0 + a_tx × t
v_rx(t) = v_rx_0 + a_rx × t
```

Where `t = 0` is the first sample of the current transmission. The resampling ratio changes smoothly over the message duration.

#### 6.2.4 Implementation: Farrow Interpolator

A **4th-order (piecewise cubic) Farrow structure** performs the variable-rate resampling:

- Maintains a fractional sample accumulator `μ` that advances by `r(t)` per output sample
- When `μ` crosses an integer boundary, the input sample index advances
- The Farrow filter interpolates the input signal at the fractional position
- Computational cost: approximately 5 multiply-accumulate operations per output sample
- With acceleration, `r(t)` is updated per output sample as velocity changes linearly

#### 6.2.5 Bulk vs. Per-Tap Doppler

**MVP: Bulk Doppler (single resampler per channel, applied before multipath filter).**

Rationale:
- The Doppler difference between multipath taps due to different geometric path angles is proportional to `(v/c)(1 − cos Δθ)`. For `v = 3 m/s` and `Δθ = 30°`, this is `~2.6 × 10⁻⁴` or 0.026% — below the resolution of typical modem receivers and the simulator's other error sources.
- Clock-offset Doppler (identical for all taps) typically dominates.
- Bulk resampling uses one Farrow instance per channel vs. N instances for per-tap.

**Post-MVP:** Per-tap Doppler can be enabled when Bellhop provides per-ray arrival angles and 3D velocity vectors are available. The architecture exposes the resampler as a callable stage that can be placed either before the multipath filter (bulk) or within each tap (per-tap).

### 6.3 Multipath

#### 6.3.1 Tap Representation

Each multipath tap is a complex-valued component representing a macro-path (e.g., direct, surface bounce, bottom bounce) optionally aggregating micro-paths:

```c
struct MultipathTap {
    float delay_s;      // Propagation delay in seconds (0 to 0.200)
    float gain_linear;  // Amplitude gain (linear scale, includes spreading/absorption for this path)
    float phase_rad;    // Phase shift in radians (accounts for reflections, micro-path aggregation)
};
```

Complex application per output sample:

```
y[n] += tap.gain_linear × ( cos(tap.phase_rad) × x[n - delay_samples]
                           − sin(tap.phase_rad) × x̂[n - delay_samples] )
```

Where `x̂` is the Hilbert transform of `x` (needed to apply a phase rotation to a real-valued passband signal). Alternatively, the phase shift can be applied as a fractional-sample delay offset within the Farrow interpolator for each tap, avoiding an explicit Hilbert transform.

**Practical MVP simplification:** If micro-path phase effects are not critical for initial testing, taps can be applied as real-valued gains and the phase field zeroed. The data structure and processing pipeline should still support complex taps from the start to avoid refactoring.

#### 6.3.2 Delay Line

The multipath filter uses a **circular buffer** (tapped delay line):

| Parameter | Value at 500 kSPS |
|---|---|
| Maximum delay | 200 ms |
| Buffer length | 100,000 samples |
| Buffer memory | 200 KB (float) or 400 KB (double) per channel |
| Number of taps | Configurable, default 10, compile-time max 32 |
| Computation per output sample | 10 complex multiply-accumulates (negligible) |

For N_modems = 6 (30 channels), total delay buffer memory: 30 × 400 KB = 12 MB. Trivial.

#### 6.3.3 Multipath Tail After TX Ends

When a modem finishes transmitting, the last TX samples remain in the delay line. **The host must continue reading out the multipath filter for up to `max_tap_delay` (200 ms) after the final TX sample enters the filter**, flushing the remaining multipath arrivals into the receiver's RX stream. During this tail period, the delay line input is zero (no new TX signal), and the output is the decaying arrivals of the last portion of the message plus ambient noise.

#### 6.3.4 Tap Configuration

MVP: Taps are statically defined in the scenario configuration file and remain fixed for the duration of the scenario.

Post-MVP: Taps are computed by ray-tracing tools (e.g., Bellhop) and updated at a configurable rate (target: 20 ms update period, subject to computational feasibility). Tap interpolation between updates will be needed to prevent discontinuities.

### 6.4 Path Loss

Frequency-dependent path loss models absorption and geometric spreading.

#### 6.4.1 Absorption: Thorp Model

Absorption coefficient `α(f)` in dB/km as a function of frequency `f` in kHz:

```
α(f) = 0.11 f² / (1 + f²) + 44 f² / (4100 + f²) + 2.75 × 10⁻⁴ f² + 0.003
```

(Valid for frequencies below ~400 kHz; coefficients for seawater. Freshwater uses modified coefficients with lower absorption.)

#### 6.4.2 Geometric Spreading

Selectable spreading law:

| Model | Loss (dB) | Typical use |
|---|---|---|
| Spherical | `20 log₁₀(R)` | Deep water, short range |
| Cylindrical | `10 log₁₀(R)` | Shallow water, long range |
| Hybrid | `k log₁₀(R)`, k configurable (10–20) | General |

#### 6.4.3 Combined Path Loss

Total transmission loss for range `R` (meters) at frequency `f`:

```
TL(R, f) = k × log₁₀(R) + α(f) × R / 1000    [dB]
```

#### 6.4.4 Implementation

For a wideband signal, path loss is frequency-dependent and must be applied as a **filter**, not a scalar gain. Implementation options:

- **FIR filter** designed from the `TL(R, f)` response across the signal band (25–35 kHz). For moderate variation across the 10 kHz bandwidth, a short FIR (8–32 taps) suffices.
- **MVP simplification**: If the path loss variation across the 10 kHz signal bandwidth is small (which it typically is for ranges < 5 km), a single scalar gain at the center frequency (30 kHz) can be used, deferring the filter implementation.

In the MVP, each multipath tap can encode its own path-specific loss in `gain_linear`, so the path loss filter stage can be folded into the tap gains for static scenarios. A separate path loss filter becomes necessary when taps are updated dynamically (post-MVP Bellhop integration) and the scenario needs frequency-dependent loss beyond what tap gains encode.

### 6.5 Transducer Response (TVR / RVR)

*Post-MVP for filtering. MVP provides data structures and configuration.*

#### 6.5.1 TVR (Transmit Voltage Response)

Describes the acoustic source level produced per volt of transducer drive, as a function of frequency. Applied to the TX signal to convert from electrical to acoustic domain.

#### 6.5.2 RVR (Receive Voltage Response)

Describes the open-circuit voltage produced at the transducer terminals per unit acoustic pressure, as a function of frequency. Applied to the received acoustic signal to convert back to the electrical domain.

#### 6.5.3 Data Format

Transducer responses are stored as **frequency-response lookup tables** in the scenario configuration:

```yaml
transducer_models:
  - id: \"tx100\"
    tvr:  # Transmit Voltage Response
      frequencies_hz: [20000, 22000, 24000, ..., 40000]
      magnitude_db:   [135.2, 137.1, 140.5, ..., 132.0]
      phase_deg:      [-12.0, -8.5, -3.2, ..., -25.0]
    rvr:  # Receive Voltage Response
      frequencies_hz: [20000, 22000, 24000, ..., 40000]
      magnitude_db:   [-180.5, -178.2, -175.0, ..., -183.0]
      phase_deg:      [5.0, 3.2, 1.0, ..., 8.5]
```

Each modem in the scenario is assigned a transducer model. Different modems can use different transducers.

**Post-MVP:** A parametric model (RLC equivalent circuit) can be used to generate the frequency response from component values, avoiding the need for measured lookup tables. The first modem's transducer equivalent circuit data is available for this purpose.

#### 6.5.4 Voltage-to-Current Conversion (Post-MVP)

The transducer's impedance model converts the captured drive voltage to the current actually flowing through the transducer, providing more realistic phase information. Implemented as a filter derived from the transducer equivalent circuit (RLC network → transfer function → IIR filter).

### 6.6 Ambient Noise

#### 6.6.1 Spectral Model: Wenz Curves

Background ambient noise follows the **Wenz spectral model**, which describes noise spectral density as a function of frequency for various ocean conditions:

| Noise source | Frequency range | Character |
|---|---|---|
| Turbulence | < 10 Hz | Low-frequency, not relevant for 25–35 kHz band |
| Shipping | 10–1000 Hz | Below band, but tail may contribute |
| Wind/sea state | 1–100 kHz | **Primary contributor** in the 25–35 kHz signal band |
| Thermal noise | > 50 kHz | Rises with frequency, contributes at upper band edge |

For the 25–35 kHz signal band, the dominant ambient noise is **wind-driven surface agitation** (sea state dependent) and **thermal noise**.

#### 6.6.2 Implementation

1. Generate white Gaussian noise at the simulation sample rate.
2. Apply a **shaping filter** designed from the Wenz spectrum for the configured sea state and environment (shallow water, deep water, harbor, etc.).
3. Scale the shaped noise so that its level at the modem's pre-amplifier input (after accounting for input attenuation) exceeds the modem-reported `noise_floor` by a configured margin.

The noise shaping filter is a relatively short FIR or low-order IIR filter since the Wenz spectrum is smooth. It is designed once per scenario (sea state and environment are static in the MVP).

#### 6.6.3 Narrowband Tonal Sources

Configurable **continuous narrowband sources** (e.g., distant shipping, mechanical equipment) can be added as sinusoidal components or narrow-band filtered noise at specified frequencies and levels:

```yaml
noise:
  wenz_sea_state: 3
  environment: \"shallow_saltwater\"
  tonal_sources:
    - frequency_hz: 27500
      level_db_re_noise: 15   # dB above ambient at this frequency
      bandwidth_hz: 50        # 0 for pure tone, >0 for narrowband noise
    - frequency_hz: 31000
      level_db_re_noise: 10
      bandwidth_hz: 100
```

MVP: Continuous tonal sources only. Post-MVP: Intermittent/transient sources (e.g., snapping shrimp: broadband impulses at random intervals) and directional noise.

#### 6.6.4 Noise Injection Point

Noise is added **after** all channel contributions are summed (step [9] in §6.1) and **before** the final DAC conversion. The noise is common to the receiver — all channels into a given modem share the same ambient noise floor. This is physically correct: ambient noise is a property of the receiver's environment, not of a specific source-receiver path.

### 6.7 Signal Combination

When multiple modems transmit simultaneously (or their multipath tails overlap in time), the receiving modem's RX stream is the **linear sum** of all individually-processed channel outputs plus ambient noise:

```
RX_B[n] = Σ_A (channel_A→B[n]) + noise_B[n]
```

For the MVP with 2 modems and no simultaneous TX, at most one channel contributes at a time (plus its multipath tail). The summing infrastructure is still implemented to support future multi-modem scenarios.

**Saturation handling:** The modem provides two selectable input attenuation levels (30 dB apart). In scenarios where the summed signal could clip the 12-bit DAC range, the host can command the modem to switch to the higher attenuation setting. MVP does not implement automatic attenuation switching; clipping is accepted as unlikely in 2-modem scenarios.

## 7. Timing and Synchronization

### 7.1 Buffer Management

Each modem maintains a **30 ms circular buffer** for the active stream (RX or TX):

| Parameter | Value at 500 kSPS |
|---|---|
| Buffer duration | 30 ms |
| Buffer capacity | 15,000 samples |
| Buffer memory | 30 KB |

**Pacing strategy:** The host targets maintaining the modem's RX buffer at approximately **50% fill** (15 ms). The modem reports buffer fill level via the control interface. The host adjusts its transmit rate to converge on the target:

- If fill level drops below target → host sends packets slightly faster (burst)
- If fill level rises above target → host sends packets slightly slower (hold)
- Underrun/overrun flags indicate the host is failing to maintain pace

The 15 ms half-buffer provides margin for USB jitter (typically 1–3 ms for bulk transfers on a low-latency Linux system).

### 7.2 Latency Budget

The total system processing latency must be **less than the simulated acoustic propagation delay**. The minimum propagation delay is 100 ms (150 m at 1500 m/s).

**Latency breakdown (worst case):**

| Component | Typical | Worst case | Notes |
|---|---|---|---|
| Modem A TX buffer accumulation | 0.5 ms | 1 ms | One packet = 0.51 ms at 500 kSPS |
| USB transfer A → host | 1 ms | 3 ms | Bulk transfer latency |
| Host channel processing | < 1 ms | 2 ms | 10-tap multipath + resampling + noise |
| USB transfer host → B | 1 ms | 3 ms | Bulk transfer latency |
| Modem B RX buffer target | 15 ms | 15 ms | Half of 30 ms buffer |
| **Total** | **~19 ms** | **~24 ms** | |
| **Margin** (100 ms budget) | **~81 ms** | **~76 ms** | Comfortable |

The generous margin means that even significant USB jitter or processing spikes will not cause late delivery. For scenarios with modem separation > 150 m, the margin increases proportionally.

### 7.3 TR Switch Settling

After a modem finishes transmitting, the TR switch requires a minimum of **200 ms** to settle before the receive path is active. During this period:

- The modem reports SETTLING state
- The host does not expect to deliver meaningful signal data
- The host may begin pre-filling the modem's RX buffer with noise so that when the modem transitions to RX, the buffer is already at target fill level

This 200 ms settling time is an important constraint for loopback mode (see §8).

### 7.4 Inter-Modem Time Alignment

**MVP approach:** No explicit common time base between modems. The host uses **USB arrival time of the first TX data packet** as the reference time for a transmission. The host's system clock (monotonic, nanosecond resolution via `clock_gettime(CLOCK_MONOTONIC)`) provides the common time reference.

Accuracy: USB arrival time has jitter of ~1–3 ms. Given the 100 ms minimum propagation delay and typical message durations of 0.1–5 s, this jitter is acceptable. It introduces at most ~1–3 ms of timing uncertainty on the simulated propagation delay, which is well below perceptual or protocol-level significance.

**Post-MVP:** For sub-millisecond time alignment (needed for precise TDOA testing or synchronized networks), the interrupt-based mechanism will be implemented: each modem drives a shared open-drain GPIO line to signal TX start. The host captures the interrupt timestamp and distributes precise timing information to all modems via control packets.

## 8. Operating Modes

### 8.1 Standard Mode (2+ Modems)

The primary operating mode with two or more modems connected:

1. Host discovers and calibrates each modem
2. Host loads scenario configuration
3. All modems enter HIL mode, receive continuous noise on their RX streams
4. When a modem transmits, its TX stream is captured, processed through the channel model, and delivered as RX to the other modem(s)
5. Multiple transmissions can overlap in time at the receiver (summed)
6. Scenario runs until stopped by the operator

### 8.2 Loopback Mode (Single Modem)

For single-modem testing, the host routes a modem's TX back to itself as RX:

1. One modem connected; host loads a loopback scenario
2. The modem transmits; host captures and buffers the entire TX stream
3. Host applies channel processing (multipath, loss, noise, Doppler) to the buffered TX
4. The modem finishes TX, enters SETTLING (200 ms TR switch)
5. After settling, the modem enters RX mode
6. Host delivers the processed signal as RX

**Minimum loopback delay:** message duration + 200 ms (TR settling) + host processing time. The scenario defines a multipath tap with sufficient delay to account for this. Operationally, this means the simulated reflector is at a range of at least `(message_duration + 200 ms) × c / 2` meters.

**Loopback with channel:** The loopback scenario can define any number of multipath taps (representing reflections from distant surfaces), path loss, Doppler, and noise, exactly as in the multi-modem case. The single tap with \"long delay, relatively low loss\" is the simplest configuration.

## 10. Host Software Architecture

### 10.1 Application Structure

The host application is a **multithreaded C++20** command-line program running on Linux.

```
┌────────────────────────────────────────────────────────────────┐
│                        Host Application                        │
│                                                                │
│  ┌──────────────┐  ┌──────────────┐       ┌──────────────┐    │
│  │  USB I/O     │  │  USB I/O     │       │   Channel    │    │
│  │  Thread      │  │  Thread      │  ...  │  Processing  │    │
│  │  (Modem A)   │  │  (Modem B)   │       │  Thread      │    │
│  └──────┬───────┘  └──────┬───────┘       └──────┬───────┘    │
│         │                 │                      │             │
│         │    Lock-free    │    Lock-free         │             │
│         │   Ring Buffers  │   Ring Buffers       │             │
│         │                 │                      │             │
│         └────────────────►├──────────────────────┘             │
│                           │                                    │
│  ┌────────────────────────┴───────────────────────────────┐    │
│  │                   Main / Control Thread                 │    │
│  │  - Scenario loading                                    │    │
│  │  - Modem discovery & calibration                       │    │
│  │  - State coordination                                  │    │
│  │  - Logging management                                  │    │
│  │  - (Optional) Live metrics display                     │    │
│  └────────────────────────────────────────────────────────┘    │
└────────────────────────────────────────────────────────────────┘
```

### 10.2 Threading Model

| Thread | Core affinity | Role | Count |
|---|---|---|---|
| **Main/Control** | Any | Scenario loading, modem lifecycle, coordination, CLI | 1 |
| **USB I/O** | Pinned | Per-modem: reads TX packets, writes RX packets, reads control packets | 1 per modem |
| **Channel Processing** | Pinned | Reads TX buffers, applies channel model, writes to RX buffers, generates noise | 1 (MVP) |

**MVP: 4 threads** for 2 modems (1 main + 2 I/O + 1 processing).

**Post-MVP scaling:** The channel processing thread becomes the bottleneck with more modems and complex channels. The architecture supports splitting into:
- One processing thread per receiver (each receiver sums all incoming channels)
- Or one processing thread per channel pair
- Lock-free ring buffers between threads enable this decomposition without changing the I/O or control threads

### 10.3 Data Flow

```
                    Modem A                                     Modem B
                    (TX mode)                                   (RX mode)
                       │                                           ▲
                       │ USB                                  USB  │
                       ▼                                           │
              ┌────────────────┐                          ┌────────────────┐
              │  I/O Thread A  │                          │  I/O Thread B  │
              │                │                          │                │
              │ Read TX pkts   │                          │ Write RX pkts  │
              │ Write ctrl     │                          │ Read ctrl      │
              └───────┬────────┘                          └───────▲────────┘
                      │                                           │
                      │ Lock-free                     Lock-free   │
                      │ SPSC ring                     SPSC ring   │
                      ▼                                           │
              ┌───────────────────────────────────────────────────┤
              │              Channel Processing Thread            │
              │                                                   │
              │  1. Dequeue TX samples from Modem A buffer        │
              │  2. Convert to float                              │
              │  3. Doppler resample (Farrow)                     │
              │  4. Multipath filter (tapped delay line)          │
              │  5. Path loss scaling                             │
              │  6. Add ambient noise                             │
              │  7. Convert to DAC format                         │
              │  8. Enqueue RX samples to Modem B buffer          │
              └───────────────────────────────────────────────────┘
```

**Ring buffer sizing:**

Each lock-free SPSC (single-producer, single-consumer) ring buffer holds at least 2× the modem buffer duration to absorb processing jitter:

| Buffer | Duration | Samples at 500 kSPS | Memory |
|---|---|---|---|
| TX input (per modem) | 60 ms | 30,000 | 120 KB (float) |
| RX output (per modem) | 60 ms | 30,000 | 120 KB (float) |
| Multipath delay line (per channel) | 200 ms | 100,000 | 400 KB (float) |

### 10.4 Libraries and Dependencies

| Domain | Recommended Library | Rationale |
|---|---|---|
| USB I/O | **libusb** (1.0) | Cross-platform, well-supported, async transfer API |
| DSP / FFT | **FFTW3** or **PocketFFT** | If FIR filters are implemented via FFT overlap-save; otherwise direct convolution suffices for short filters |
| Resampling | **Custom Farrow implementation** | Simple enough (~50 lines) to avoid a dependency; libsamplerate does not support time-varying ratio |
| YAML parsing | **yaml-cpp** | Standard C++ YAML library |
| Lock-free queues | **Boost.Lockfree** or **custom SPSC ring** | SPSC ring is ~100 lines; Boost provides well-tested implementations |
| Logging | **spdlog** | Fast, header-mostly, supports async logging |
| Math | **Standard `<cmath>`** | No need for Eigen given the simple linear operations |
| Testing | **Google Test** or **Catch2** | Unit testing the channel model components |

### 10.5 Raw Stream Logging

The host logs raw streams to disk for post-analysis:

| Stream | Format | Content |
|---|---|---|
| TX capture (per modem) | WAV (16-bit) or raw binary | Unprocessed TX samples as received from modem |
| RX injection (per modem) | WAV (16-bit) or raw binary | Final RX samples as sent to modem |
| (Optional) Processed signal | WAV or raw binary | Post-channel, pre-noise signal for diagnostic |

WAV files use the modem-reported sample rate. File names include modem ID and timestamp. Logging runs in the main thread (or a dedicated low-priority thread) reading from the ring buffers, so it does not impact real-time processing.

### 10.6 Live Metrics (Optional MVP)

Printed to `stdout` or a status line at ~1 Hz:

- Per-modem: buffer fill level (%), current state (TX/RX/SETTLING), dropped packets
- Processing: channel processing latency (μs per block), instantaneous Doppler ratio
- System: CPU utilization per pinned core
